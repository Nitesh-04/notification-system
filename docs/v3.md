# Notification System V3

## Purpose

V3 changes notification processing from one event-level worker into a scalable notification-task system.

V2 receives one event message and then one worker loops through every subscriber. V3 fans out that work into individual notification tasks so multiple workers can process users in parallel.

## Architecture

```text
Sports Event API
        |
        +-- Save Event to PostgreSQL
        +-- Publish EventCreated
                    |
                    v
              event-created topic
                    |
                    v
             Event Fan-out Worker
                    |
                    +-- Find matching subscribers
                    +-- Resolve channel preference/event route
                    +-- Publish one task per user/channel
                                |
                                v
             v3-email-notifications     v3-push-notifications
                  /       |       \          /       |       \
                 v        v        v        v        v        v
             Email workers (group)       Push workers (group)
                        |                         |
                        +-- Claim task atomically in PostgreSQL
                        +-- Rate limit provider calls
                        +-- Deliver through channel provider
                        +-- Save SENT or FAILED
                        +-- Retry, then send to channel DLQ
```

The application may still begin as one Spring Boot repository. The important change is that the workload is split into independently consumable notification tasks.

## V3 event flow

```text
POST /events/create
        |
        v
Save sports event
        |
        v
Publish eventId to event-created
        |
        v
Event fan-out worker receives event
        |
        +-- Fetch matching subscribers
        +-- Publish one NotificationTask per subscriber/channel
        |
        v
Notification workers consume individual tasks
        |
        +-- Send through the email or push worker
        +-- Respect provider rate limits
        +-- Save delivery result
```

Example task:

```json
{
  "eventId": 41,
  "userId": 5,
  "userEmail": "user@example.com",
  "channel": "PUSH",
  "eventName": "Arsenal",
  "payload": "Goal scored",
  "attempt": 0
}
```

`PUSH` currently uses a fake provider that logs delivery. This lets us test the
distributed flow without a mobile application; a real provider can replace it later.

## Why V3 is needed

In V2, one event with 900,000 subscribers is handled by one consumer method:

```text
one event message
→ one worker
→ loop through 900,000 users
```

Kafka can store the event, but it cannot parallelize the loop inside that method.

V3 changes this to:

```text
one event
→ 900,000 notification tasks
→ multiple partitions
→ multiple workers process tasks in parallel
```

## Kafka design

V3 uses separate topics for separate workloads:

```text
event-created
    → event fan-out worker

v3-email-notifications
    → email notification workers

v3-push-notifications
    → push notification workers

v3-email-notifications.dlq / v3-push-notifications.dlq
    → permanently failed messages for inspection or manual recovery
```

The number of Kafka partitions controls the maximum parallelism available to a consumer group. Running more workers than partitions does not increase processing parallelism.

For notification tasks, a key such as `(eventId:userId)` can identify the user-event pair and support idempotent processing.

## Rate limiting

External email providers impose limits. A worker must not send unlimited requests as soon as Kafka delivers tasks.

```text
Kafka tasks
    |
    v
Rate limiter
    |
    v
Email provider
```

Rate limiting protects the provider and prevents the application from being throttled. It may be implemented per worker initially and later coordinated across workers when a global provider limit is required.

## Retry and dead-letter behavior

Temporary failures are retried:

```text
notification task fails
→ publish retry message
→ retry worker attempts delivery again
```

After the retry limit is reached:

```text
retry limit reached
→ mark notification FAILED
→ publish or retain the message in a dead-letter flow
```

A dead-letter queue prevents a permanently bad message from blocking normal work. It also preserves the failed message for debugging and manual replay.

## Idempotency

V3 still requires protection against duplicate Kafka delivery.

The worker first atomically inserts a `PENDING` row. If another worker has
already claimed the same `(user_id, event_id, channel)` task, the insert affects
zero rows and that worker skips delivery. Only the worker that wins the claim may
call the provider. The database constraint is:

```text
(user_id, event_id, channel) must be unique
```

The notification worker must treat a duplicate as already processed rather than sending the same notification repeatedly.

For external providers, a provider-supported idempotency key should eventually use the user-event pair as well.

## Monitoring goals

V3 needs metrics for both throughput and backlog:

```text
notification tasks created
notification tasks processed
notifications sent
notifications failed
retry attempts
dead-letter messages
email delivery time
worker processing time
Kafka consumer lag
rate-limit waits
```

The V2 statistics endpoint can continue exposing calculated summaries. V3 additionally needs queue and worker metrics to show where work is accumulating.

## V2 versus V3

| Concern | V2 | V3 |
|---|---|---|
| Kafka event | One event message | One event message plus notification tasks |
| Notification work | One worker loops subscribers | Workers process individual tasks |
| Parallelism | Limited within one event | Controlled by partitions and workers |
| Email delivery | Worker sends directly | Rate-limited channel workers |
| Retry handling | Retry topic | Retry topic plus dead-letter flow |
| Scaling | Mainly scale the application | Scale notification workers independently |
| Monitoring | Counters, timers, summary stats | Queue lag, throughput, rate limits, DLQ |

## Existing database migration

`ddl-auto=update` adds the new `channel` column, but it does not reliably change
an existing PostgreSQL unique constraint. On an existing V2 database, run this
once before testing two channels for the same user and event:

```sql
ALTER TABLE notification
    DROP CONSTRAINT IF EXISTS unq_notification_user_event;

ALTER TABLE notification
    ADD CONSTRAINT unq_notification_user_event
    UNIQUE (user_id, event_id, channel);
```

Existing V2 rows have a null channel and remain readable. New V3 tasks use an
explicit channel.
