# Notification System V2

## Purpose

V2 introduces asynchronous notification processing. The event API will no longer create every notification during the original HTTP request.

The goal is to separate accepting an event from processing its notification workload.

## Architecture

```text
Client
  |
  v
Event API
  |
  +-- Save Event to PostgreSQL
  |
  +-- Publish EventCreated message
          |
          v
      Message Broker
          |
          v
      Notification Worker
          |
          +-- Read event message
          +-- Find matching subscriptions
          +-- Create notification records
          +-- Acknowledge message
          |
          v
      PostgreSQL
```

V2 can still remain in one repository and use one Spring Boot application initially. The important change is the queue and worker boundary, not immediately splitting the code into many deployable services.

## New event flow

```text
POST /events/create
        |
        v
Save Event
        |
        v
Publish EventCreated message
        |
        v
Return response quickly

Worker receives EventCreated
        |
        +-- Find matching subscriptions
        +-- Create notifications
        +-- Mark processing complete
```

## What V2 improves

### Faster event responses

The request waits for the event to be saved and published, not for every notification to be created.

### Workload buffering

The broker can hold messages when events arrive faster than workers can process them.

### Independent processing speed

Notification workers can process messages in the background and can later be scaled horizontally.

### Failure isolation

A worker failure does not necessarily prevent the event API from accepting new events.

### Foundation for retries

Failed messages can be retried without requiring the client to recreate the event.

## What V2 introduces

- A message broker, such as RabbitMQ or Kafka.
- An event message schema.
- A producer that publishes `EventCreated` messages.
- A consumer or background worker.
- Message acknowledgement behavior.
- Worker logging and processing status.
- Tests for messages that fail or are delivered more than once.

## Important V2 problems to solve

### At-least-once delivery

Most practical brokers may deliver a message more than once. The worker must assume duplicates are possible.

```text
Same EventCreated message twice
        |
        v
Do not create duplicate notifications
```

### Idempotency

The worker needs a way to identify whether a notification for a particular event and user has already been created or processed.

Possible protection includes a unique database constraint such as:

```text
(event_id, user_id)
```

The exact constraint depends on whether one event may intentionally produce multiple notification attempts or channels.

### Retries

A temporary failure should be retried. A permanent failure should eventually be recorded as `FAILED` or sent to a dead-letter queue.

### Transaction boundaries

V1 can use one transaction around event creation and notification creation. V2 crosses a database and broker boundary, so the system must decide what happens if:

- The event saves but publishing fails.
- The message publishes but the worker crashes.
- The notification saves but acknowledgement fails.

These are core distributed-systems problems.

## V2 does not need to do yet

- Split every class into a separate microservice.
- Add email, SMS, and push providers.
- Deploy to Kubernetes.
- Introduce multiple databases.
- Solve every delivery guarantee immediately.

The first V2 milestone should be small:

```text
Save event → publish message → consume message → create notifications
```

Then add failures, retries, and idempotency one at a time.

## V1 versus V2

| Concern | V1 | V2 |
|---|---|---|
| Event processing | Synchronous | Asynchronous |
| Notification work | Inside event request | Background worker |
| Buffer for spikes | None | Message broker |
| Request latency | Includes notification work | Mostly event save and publish |
| Failure handling | Transaction failure | Retries and acknowledgement |
| Scaling | Scale whole application | Scale workers independently |
| Duplicate messages | Not applicable yet | Must handle idempotently |
| Operational complexity | Low | Higher |
