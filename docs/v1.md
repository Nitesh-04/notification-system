# Notification System V1

## Purpose

V1 is a working synchronous notification system. It provides the complete business flow in one Spring Boot application backed by PostgreSQL.

The goal of V1 is to establish a correct baseline before introducing distributed-systems complexity.

## Architecture

```text
Client
  |
  v
Spring Boot application
  |
  +-- Controllers
  |     +-- UserController
  |     +-- SubscriptionController
  |     +-- EventController
  |     +-- NotificationController
  |
  +-- Services
  |     +-- UserService
  |     +-- SubscriptionService
  |     +-- EventService
  |     +-- NotificationService
  |
  +-- Spring Data JPA repositories
  |
  v
PostgreSQL
```

## Domain model

```text
User 1 ---- many Subscription
User 1 ---- many Notification
Event 1 --- many Notification
```

- A user can have many subscriptions.
- Each subscription belongs to one user and one event name.
- An event represents something that happened, such as an Arsenal goal.
- A single event can create many notifications.
- Each notification belongs to one user and one event.

The subscription table has a unique constraint on `(user_id, event_name)` so the same user cannot subscribe to the same event name twice.

## Event flow

```text
POST /events/create
        |
        v
EventController
        |
        v
EventService
        |
        +-- Save Event
        +-- Find matching subscriptions
        +-- Call NotificationService
                    |
                    +-- Create one Notification per subscription
                    +-- Save notifications
        |
        v
Return event response
```

The event is saved before notifications are created so that it has a generated `event_id`.

## API endpoints

```text
GET  /users/all
GET  /events/all
POST /events/create
GET  /subscriptions/all
POST /subscriptions/create
GET  /notifications/event/{eventId}
```

Request example:

```json
{
  "eventType": "GOAL",
  "eventName": "Arsenal",
  "payload": "Saka scored"
}
```

## Strengths

- Simple to understand and run.
- One deployment and one database.
- Straightforward transactions.
- Easy local debugging.
- Correct user, subscription, event, and notification relationships.
- DTOs prevent internal JPA entities and lazy-loading metadata from leaking through the API.
- Validation and duplicate-subscription protection are present.

## Limitations

Notification creation is synchronous:

```text
The event request waits for every notification insert.
```

As the subscriber count grows:

- Request latency increases.
- The event API and notification processing compete for the same resources.
- A notification-processing failure can fail the event transaction.
- There is no queue to absorb traffic spikes.
- There is no background retry mechanism.
- A process crash can interrupt a large notification batch.
- Notification delivery is currently represented by database records; external email, push, or SMS delivery is not implemented.

## V1 load-test observation

The system was tested with thousands of subscribers. Processing time increased from roughly hundreds of milliseconds for around 1,000 notifications to around two seconds for several thousand notifications.

- 20 users - 140ms
- 100 users - 420ms
- 1000 users - 1.2s
- 5000 users - 4.2s - 4.4s (bottleneck clear)
- 10000 users - 5s
- 900000 users - yes 9 lakh - 5 minutes 25s (laptop burning)

This establishes the reason for V2: V1 works (does it tho), but the event request is responsible for all notification work.
